# Architecture

A local-first Kanban board extension for OpenChamber, built with the official `@openchamber/sdk`. All task and preference data lives in `host.storage` on the connected OpenChamber server — nothing is sent anywhere else, and no capability beyond what's listed below is used.

Requires OpenChamber `>=1.24.0` — the Extensions SDK (`Settings → Extensions`, panels, pages, `host.storage`) doesn't exist in earlier versions. The `microphone` capability additionally needs an OpenChamber that ships SDK 2.7.x (ready.features.microphone); on older hosts the mic button simply never renders.

## Manifest and capabilities

```jsonc
{
  "openchamber": {
    "apiVersion": 1,
    "engines": { "openchamber": ">=1.24.0" },
    "contributes": {
      "panel": { "id": "kanban-board", "name": "Kanban", "icon": "task", "entry": "panel/frame.html", "mobile": true },
      "page": { "entry": "panel/page.html", "title": "Kanban board", "mobile": true },
      "capabilities": ["sessions", "prompt", "microphone"],
      "service": { "entry": "service/main.js", "runtime": "host", "keepRunning": true, "permissions": { "exec": ["git"] } }
    }
  }
}
```

| Capability | Used for |
|---|---|
| `sessions` | `listProjects`/`onProjects`, `listSessions`/`onSessions`, `listWorktrees`/`onWorktrees`, `startSession`, `openSession` — reading project/session/worktree state and creating or opening sessions. |
| `prompt` | Permits `host.prompt`: with `send` omitted it replace-composes text on the current session — `fillComposerAfterOpen` (`promptFill.ts`) writes it immediately and again once the session switch settles, because the host fills a single global composer slot and a fill can silently lose the switch race (see the SDK limitations). |
| `microphone` | Voice dictation for the description field (`host.openMicrophone`), see "Voice dictation" below. Audio is processed on this machine only. |
| `service` (auto-added by declaring `contributes.service`) | The local git-branch-reading and dictation service, see below. |

**Capability approval is all-or-nothing.** The host's own grant endpoint (`PUT /api/guests/:id/capabilities`) accepts only the full requested list or `[]` — there is no partial grant. Installing this extension means accepting all four capabilities together; there is no way to get the Kanban board without also being asked about the microphone and the local service.

```

      sync.ts            # agent activity → task status mapping — pure
      boardView.ts         # the one view model both surfaces render: display-only agent regrouping, unseen flags, badge counts — pure
      viewMode.ts         # the panel frame's view rule: quick-actions mirror vs interactive board, from width + device — pure
      worktree.ts         # worktree/branch picker logic, local service response parsing — pure
      unlink.ts            # link health: whether a linked session/worktree provably still exists — pure
      autoTask.ts          # orphan-session eligibility + initial status + title — pure
      chatLink.ts        # the rail's chat button: the startSession request for a task, the link patch its success writes, and the composer-fill text (extension id + chip url) — pure
      agentChannel.ts      # the agent channel's wire model: journal entry + mirror parsing, directory→project mapping, mirror cutting for the request-body cap, and the pure board-apply plan — pure
    store/
      taskStore.ts      # one host.storage key per task: task:<id>
      taskOps.ts          # the write ops the full-screen page runs: moves (planMove/saveMove/statusMove), bulk moves (planStatusMoves in domain/board.ts), createBacklogTask, patches, deletes (single + batch, the dismissal-before-delete protocol) — pure + storage only
      adoptOps.ts         # the one session-adoption write every open surface runs (page + rail mirror): fresh-read dedupe, end-of-column rank, same-instant twin convergence by id tie-break — pure + storage only
      titleOps.ts         # the one title-promotion write adoption leaves open: a placeholder-titled card takes its session's real title — fresh-read re-check (never a renamed card), clamped, converged by value — pure + storage only
      prefs.ts            # board filters + last-open task: host.storage key "prefs"
      orphanWatermark.ts    # "going forward" cutoff timestamp: host.storage key "orphan-watermark"
    host/
      workspace.ts      # host.listProjects/onProjects/onSessions/onWorktrees/openSession wrappers
      agentChannel.ts       # the board's side of the agent channel: mirror push, journal pull + ack — best-effort, null on any service failure
      sessionSync.ts      # live onSessions watcher → status sync (page) + the live map both surfaces display from
      worktreeSync.ts       # live onWorktrees watcher → worktree-deleted unlinks
      autoDoneSync.ts       # the auto-done rule's watcher: commit checks via the service route, observed-read marker clears, guarded Done writes
      titlePromotion.ts   # the title promotion's watcher: carries the live snapshot's session titles to adoption's placeholder-titled cards, one attempt per session — silent
      orphanSessions.ts     # live onProjects+onSessions watcher → sessions with no task yet
      branchService.ts        # calls the local git-branch service; null on any failure
      dictation.ts            # mic capture state machine + chunked /transcribe client
    ui/
      dnd.ts            # drop-target math — pure, no DOM
      styles.ts           # CSS using the host's --oc-* theme tokens
      dom.ts                # element() helper
      pill.ts             # the agent-state pill (cards, rail rows, dialog head): tint from the kit's tone variables, glyph per state
      speech.ts               # resample/Int16/base64 chunk helpers — pure, no DOM
      kanbanView.ts          # the one renderer both surfaces mount (page = columns, rail = sections): every interactive affordance is conditional on the handler the surface supplies
      board.ts               # the page: toolbar + selection bar + column-empty arming + detail dialog + the agent-status writer, adoption, reconciliation — around kanbanView
      detail.ts               # task detail dialog (opens only on the page: ✕ close, task-body actions row, root-only Start Agent)
      dictationPanel.ts         # dictation controls used by the detail dialog
    page.ts             # full-screen page entry (contributes.page)
    panel.ts              # one-surface rail entry (spare shell): mounts the mirror once per frame lifetime
    panelMirror.ts          # the mirror itself, mountable: kanbanView rail mode, display data + the panel's two carve-outs (onMarkDone + onChat) + the page's live adoption (scoped to the panel's project), full dispose of its subscriptions for the frame's swaps
    frame.ts              # the adaptive panel entry behind the rail icon (contributes.panel): mounts the mirror or the page's board factory by width + device (viewModeFor), swapping live on the host's resize
    service/
      main.ts           # bootstrap: env, server, git + real recognizer (Node, not browser)
      server.ts         # the loopback HTTP surface: auth (host token + agent token), body read, route dispatch
      agentStore.ts       # the channel's persistent state: mirror.json + journal.jsonl, atomic writes, serialized rewrites

  skill/
    kanban/SKILL.md       # the agent-facing instructions (routes, discovery, etiquette) — installed into the user's OpenCode skills dir
  panel/
    index.html, frame.html, page.html   # HTML shells
    main.js, frame.js, page.js          # esbuild IIFE output
  service/
    main.js             # esbuild Node/ESM output of src/service/main.ts (sherpa-onnx-node stays external)
  test/                 # node:test unit tests for domain/, store/, host/, plus the service HTTP routes
  scripts/build.mjs      # esbuild: browser IIFE for panel/page, Node/ESM for the service
```

Layering: `domain/` has no SDK or DOM imports — pure functions, fully unit-tested. `store/` and `host/` depend only on narrow `Pick<HostClient, …>` slices, tested with in-memory fakes. `ui/` is the only layer that touches the DOM.

## Task data model

```ts
type Task = {
  schemaVersion: 1;
  id: string;                 // t_<base36 time><6 random chars>
  title: string;
  description: string;        // the text a new chat's composer is pre-filled with (else the title); nothing is sent until you press send
  status: 'backlog' | 'todo' | 'in_progress' | 'review' | 'done';
  rank: number;                // fractional, for drag-and-drop ordering within a column
  projectId: string | null;
  sourceBranch: string | null;    // the worktree-first auto-done evidence path; no current flow records it (see "The auto-done rule")
  worktree: { directory: string; branch: string | null } | null;
  sessionId: string | null;
  createdAt: number;
  updatedAt: number;
  needsAttentionSince: number | null;  // set when the Review marker/sort should treat this as unseen
  sessionLinkedAt: number | null;      // the auto-done anchor: when the session was linked; its commits count from here
  agentNotes?: AgentNote[];            // notes agents left through the agent channel ({ at, text } each); absent on tasks that never received one
};
```

Stored one task per `host.storage` key (`task:<id>`), so editing one task can never corrupt another, and a malformed record is reported and skipped rather than blocking the rest of the board. Board filters, the currently-open task, and the "going forward" orphan-adoption cutoff are each a separate key (`prefs`, `orphan-watermark`).

## The board

Full-screen page (`contributes.page`) with a project filter and five columns (Backlog, To Do, In Progress, Review, Done). The rail panel is the same kanban view in an adaptive frame — the **display-only mirror**, locked to the open project, at rail widths; the page's own interactive board when a desktop panel is expanded (see "The rail panel"). Everything interactive beyond the panel's two quick actions lives on the page — or in the panel's board mode, which is that page.

- **One view, two surfaces.** The page and the rail mirror mount the same renderer (`src/ui/kanbanView.ts`) and render the same pure view model (`src/domain/boardView.ts`, `buildBoardView`). Only the layout differs because the width does: columns of cards versus stacked sections. Every interactive affordance in the renderer is conditional on the handler the surface supplies — the page passes the full set (tap, ⋯ menu, drag, fold, selection, column-empty); the rail mirror passes `onMarkDone` and `onChat`, its two deliberate actions; and when the rail's frame is expanded wide on a desktop, the adaptive frame mounts the page's own factory (`mountKanbanBoard`), so the full set lives in the panel too (see "The rail panel" below). The writes of all these surfaces run through one shared module (`src/store/taskOps.ts`), so the ordering any of them displays can never disagree with the orderings another writes.
- **Add task** is a single **+** icon button in the toolbar (the toolbar's other icon is the reload — it spins while a reload runs, and every reload, whatever triggered it, keeps that visible). A click creates a real, persisted task immediately (title `"New task"`, appended to Backlog via the shared `createBacklogTask`) and opens its detail popup for editing — no separate title field in the toolbar.
- **Card details.** Every item — card or rail row — shows the same body: title, project name, and the agent **pill** (`src/ui/pill.ts`: the same tint as the host's own toned badges — the kit resolves its `data-tone` to the app's real status colors — plus a glyph: ▷spinner running, ? needs your answer, shield needs permission, ! failed, ✓ finished; a muted dot for "idle"/"chat linked") — the pill is the one status signal an item wears, so an agent-driven move shows as the row's new column or section, and small icon buttons where handlers exist: on the page, a success-tinted ✓ beside the ⋯ menu (the mark-Done shortcut) and the ⋯ menu itself (Move to every other column, Edit task, Delete task); on the rail, the mark-done ✓ sits at every non-done row's right edge — always visible, tinted with the app's info tone (`data-info`, riding the `--oc-info-*` tokens `applyHostReady` paints on the frame root) — and the chat button sits beside it: **Open chat** on any linked card (filled with the primary tint on an attention row), and on an unlinked card that can receive one (a project, and not Done) the plus-cut bubble that starts one attached to the card.
- **Drag-and-drop** (page) uses fractional ranks (`planDrop`, `rankAtEnd` through the shared `planMove`/`saveMove` ops), so moving a card only ever rewrites that card and, rarely, a few neighbors whose gap became too small — never the whole column. Keyboard: page items are focusable; Enter/Space activates them.
- **Multi-select** (page) is transient board-page state — a `Set<string>` the page owns; the renderer only asks (`onToggleSelect`/`isSelected`, `data-selected` on the card). One checkbox sits left of every card's title, always visible (larger under a finger), and Ctrl/⌘-click on a card body toggles too. A selection bar appears under the toolbar while anything is selected: the count, a **Move to** menu, **Mark Done**, and a **Delete** that needs its second, confirming press. Every action runs through the shared ops — bulk move through `planStatusMoves` (in `domain/board.ts`): the selection moves as a group appended at the target column's end in the board's own rank order — not Review's urgency display order — with attention markers cleared, tasks already in the target left in rank (only a stale marker clears), and no rebalancing anywhere. Bulk delete and column emptying share `deleteTasksWithDismissal`: all fresh linked-session dismissals saved **once** before the first delete, deletes independent per storage key (one failure keeps only its own task), failed tasks' sessions un-dismissed again so a task that was not deleted keeps its session adoption-eligible. The selection survives re-renders and filter changes, is pruned on reload, and clears on Escape (waiting a beat while a detail dialog is open, which owns Escape first).
- **Column cleanup.** Every page column head carries a small trash icon beside the count pill. First press arms it — destructive tint, "Click again to empty <column>" — the second press deletes exactly the tasks currently shown in that column (the filter-respecting view: "All projects" then spans projects, which the armed confirm makes explicit), through the same `deleteTasksWithDismissal` as above. The arming is the page's state with a ~3.5 s timeout so a stray tap never leaves a column primed for deletion, and an empty column never arms at all. The rail renders none of this: it passes no selection handlers, and its single-write design is untouched.
- **Column colors.** One theme token per column, keyed off the `data-status` the renderer already puts on both surfaces (the rail's `renderSection` sets it in parity with the page's `renderColumn`; `--kb-accent` in `styles.ts`): Backlog muted, To Do the info blue held back, In Progress the same blue at full strength, Review warning, Done success. The two blues are one family at two strengths — planned vs working — split by a faded strip, a dimmer title and a lighter count tint on To Do. The theme's brand `--oc-primary` is **deliberately out of the column palette**: in real host themes it can sit anywhere on the wheel (checked against one where it lands right beside the amber), and a column must not depend on it to stay distinct. The accent paints exactly three head pieces — a 3px strip above the head, the title, the count pill — and stops there: column bodies stay neutral so the attention border, the agent pills, and the drag-over outline keep sole ownership of their hues in every column. The attention count (`data-attn`) overrides the tint with the warning color wherever the flag fires; in Review that is a shade match, not a conflict. No foreign colors: everything rides the `--oc-*` tokens `applyHostReady` paints, so both themes come free.

- **Badges.** The badge next to the toolbar shows the view's open count with unseen flags ("N open · M unseen", warning tone while unseen rows wait) — the same pill the rail header shows. The Kanban rail icon deliberately carries **no number**: `host.setBadge` is not called from any surface; the panel just displays, and a counting icon would pretend otherwise.
- **The Review column sorts by urgency**, not rank: whichever task most recently needs attention leads; already-seen tasks sink below and keep normal rank order among themselves. Every other column stays rank-ordered.

### The "needs attention" marker

A task that lands in Review through something other than your own action — the live agent-status sync or auto-adopting a running session — gets `needsAttentionSince` set to that moment, shown as a warning-colored left border on its card. It's cleared the moment you open the task (its chat, or its detail popup) or drag it anywhere yourself. A status change you make deliberately (dragging, or the detail popup's own status strip) never sets the marker — only the two automatic paths do.

### The rail panel (adaptive frame: quick-actions mirror ⇄ interactive board)

The rail icon opens one frame, `src/frame.ts` behind `contributes.panel`, that is **the quick-actions mirror at rail widths and the interactive board when the host's context panel expands — on a desktop only**. The host carries the user-facing affordance itself: a context panel's expand toggle folds the project sidebar and hands the surface nearly the whole window beside a drag-resizable chat sliver, and the frame's iframe resizes with every step, so no host change and no reload are involved. The pure rule (`viewModeFor` in `src/domain/viewMode.ts`) reads the device shape from `ready.device` (`phone`/`tablet` mount only the mirror, however wide the panel draws, so the touch layouts keep the quick actions) and the frame's own width (`document.documentElement.clientWidth`): the board comes up at 640 px and holds with a 128 px dead band either side of the threshold, so a drag that hovers near the line never flip-flops the view. One trailing pass per resize storm evaluates it; a swap disposes the mounted view first — both surfaces release every subscription they hold, so the frame's subscription cap holds whichever mode is live, and only one surface's writes are ever in play inside the frame — then mounts the other. The board in the panel is the page's own factory unchanged (`mountKanbanBoard`): same persisted filter (the `prefs` both surfaces share), writes, detail dialog, drag-and-drop, agent-status writer, adoption and column cleanup; its transient state (selection, an armed confirm, an open dialog) resets on a swap, deliberately and rarely. The mirror's logic lives in `src/panelMirror.ts` as a mountable factory — `src/panel.ts` (`panel/index.html`, kept built but no longer in the manifest) mounts it once per frame lifetime as the single-surface shell it was before the frame learned the board.

Below, what that means in the mirror's own mode — the display behavior unchanged from before the frame got this second gear, with one addition since: the mirror now runs the live session adoption the page runs (see "Live adoption" below), the one write the narrow rail makes with no click of its own.

The mirror (`src/panelMirror.ts`) is the board's view rendered for a narrow rail and stripped of every affordance but two: it mounts the same renderer (`src/ui/kanbanView.ts` in `rail` mode) and the same pure view model (`buildBoardView` in `src/domain/boardView.ts`) with `onMarkDone` and `onChat` beyond display data — no tap, no ⋯ menu, no dragging, no fold toggling, no quick-add. The renderer draws rows plain and non-focusable except for the two buttons at their right edge: the mark-done ✓ on every non-done row — always visible, tinted with the app's info tone (`data-info` on the kit-independent `.kb-iconbtn` idiom), Done rows carrying none because they need none — and the chat button beside it, Open chat on any linked card (its history is worth opening at any status) and the new-chat glyph on an unlinked card that could receive one. The mirror writes exactly two things on a click of its own — a deliberate Done, through the same pure `statusMove` op the ⋯ menu's Move-to takes (kept rank, attention marker cleared, nothing re-saved when it changes nothing); and the chat action, which opens the linked session or starts one attached to the card and saves its link through the same store helpers the page's Start Agent uses (`chatLink.ts` builds the request, the patch, and the composer-fill text — pure, like everything else in `domain/`), never a status of its own — plus the one automatic write it shares with the page, live session adoption (own bullet below): an import, never a regroup. And it does not number the Kanban rail icon either (`host.setBadge` is unused everywhere): the icon is just a way in to the same view.

- **Display-only agent sync.** The panel applies the board's own pure mapping (`statusForSession`, via the view model) to live session state and regroups rows accordingly, so a task whose linked build agent finished while the board was closed already sits under Review (the gate rides along — the view model reads the agent from the same snapshots) — the row's position carries the move; no `→` chip renders anywhere. Its agent mapping never writes the status it implies — the page stays the only writer of agent-driven status changes (its marker setting, `lastAttemptedStatus` retry guard, and save-retry logic remain in one place), and the stored status is exactly what the board will persist the next time it opens. The panel's own status writes stop at its two deliberate actions (see below) — the Done move, kept inside the same ordering (the same `statusMove` op, saved through the same store helper), and the chat link, which writes only the chat's existence, never a status; the one write beyond them is the adoption import (own bullet below), whose status is the session's live state, the same rule the page persists. The panel has no tick scheduling of its own; its 30 s idle interval pass re-renders soon after any quiet-window crossing the snapshots don't cover.
- **Unseen flags.** A stored `needsAttentionSince` marker, or an agent's display-only move into Review (no board was open to persist the marker), flags the row — warning border on the item, a summary line above the sections ("N tasks need your review"), and a warning-tone badge next to the view's open count. A marker whose linked session the host reports as opened elsewhere (`unread: false`) does not flag: the visit happened outside the board, `buildBoardItem` clears the flag for display, and the page persists the stored clear when `autoDoneSync` observes it (the rail, never a writer, checks `unread` directly). Rows under Done are excluded from the count: Done is deliberate work, not open attention. Review sections order unseen rows by the stored marker, with the session's own last-change time standing in for a marker that could never be persisted.
- **Project scope.** The panel shows only the tasks of the project OpenChamber currently has open: `ready.directory` seeds it and `host.onDirectory` keeps it current, with `projectForDirectory` mapping a directory (nested paths included) to the registered project. With no open directory — or one matching no registered project — every task shows, with the project named per row. The one-line "Project: …" scope indicator under the header names the focused project and per-row names appear only in that show-all mode. This is the whole difference from the page: on the page the scope is a filter you can change, on the panel it is locked to the open project.
- **Live data.** One `onProjects` subscription plus one `onSessions` subscription per *visible* project holding linked sessions (same per-project pattern as `sessionSync.ts`, inside the frame's subscription cap — `createSessionSync` is the shared live provider; the panel passes no `onStatusChange`). A trusted (`ready`) snapshot rebuilds that project's entries in the shared live map; `loading` keeps the last known state; an `error` drops them so rows fall back to their stored status — unknown is never displayed as new. A project leaving the visible set also has its live entries dropped, so an unsubscribed project's stale activity can never display as if it were live when it comes back into view. Every snapshot also schedules one debounced `loadTasks` read (500 ms, joined by a re-read of the discarded-session list, because the board's deletes must be honored here without the mirror ever writing that key), because storage has no change push and the board page may have saved edits meanwhile; a 30 s interval covers the idle case. A display-only surface has no Refresh button — it keeps itself fresh.
- **Live adoption, shared with the page.** The panel runs the page's own orphan watcher (`watchOrphanSessions`) against the same shared write (`store/adoptOps.ts`), started only after its first load has landed and disposed with the mirror, so a swap to the board's factory never doubles the adopter. Scoping is the panel's display: the locked project only — every registered project in show-all mode. A session that starts running, asks you something, or finishes while only the rail is open gets its card here and then, announced by the same toast wording the page uses. The page's guard set comes along: per-mount attempted ids, the in-flight `startSession` pause (the chat button's own start claims its id before the pause lifts), dismissed + linked exclusions, the persisted watermark (with its first-run initialization if this panel is the feature's first surface ever). A session another surface adopted moments ago is `null` at the fresh read; a twin born inside the same instant is converged away by the op (see "Auto-adopting a session with no task").
- **Two carve-outs, by design.** The panel performs exactly two deliberate actions, both the user's own click. Marking a task Done with the row's ✓ (nothing auto-marks): the same `statusMove` op. And the chat button beside it: on a linked card, opening that session — clearing an attention marker first when one waits, the same "opening a waiting chat is being reviewed" rule as the page; on an unlinked card, starting a chat **attached to the card** (`host.startSession`, no `text`), in the card's own worktree when it has one, else the project root, then saving the link — `sessionId` plus the host's reported worktree — with retries, `openSession` only after the last save lands (the same save-before-navigate ordering the page learned the hard way), and finally the chat's composer pre-filled with the card's description — else its title — through the shared `fillComposerAfterOpen` (`src/host/promptFill.ts`: `host.prompt` with `send` omitted, replace-compose on the now-current session, plus one settled re-write — this tail is the same one the page's Start Agent keeps): **nothing is sent** — the agent only starts when the user presses send — and never a status change from the rail: the board persists the actual move the next time it opens. Cards without a project get no button (a chat needs somewhere to run), a link save that fails all its retries navigates nowhere (the chat already exists, the toast says so, and the board's orphan adoption surfaces it to link deliberately — a duplicate in that same narrow window is the board's own corrective; the panel deletes nothing), and an open that fails stops before the fill — a description is never composed into some other chat's composer. Everything else — Edit, Move, Delete, quick-add — is a deliberate action that lives on the full board, where the dialog width for editing exists. The mirror's answer to "do something with this task" is its footer line: pull the panel wide for the full board, or the Extension pages menu — one step either way.

## Agent-status sync

Implemented in `src/domain/sync.ts` (`statusForSession`, pure) and watched live by `src/host/sessionSync.ts` (`createSessionSync`, one `host.onSessions` subscription per project among currently-linked tasks):

| Session activity / outcome | Task moves to |
|---|---|
| `running`, `retrying` | In Progress (from any status, Done included — the rework pull-back) |
| `waiting-question` | Review |
| `waiting-permission` | Review |
| `idle` + outcome `completed` | Review |
| `idle` + outcome `failed` | Review |
| anything else | no change |

Every move into Review above carries one gate: the session must run as the **build agent** at that moment. `statusForSession` takes the linked session record's `agent` field straight from the same snapshot (into `SessionLiveState.agent`, and into the write path), and `reviewEligibleAgent` opens the gate only for it, compared trimmed and lowercase. A plan, a brainstorm, or any other agent's question, permission prompt, finished or failed turn returns `null` — the card stays exactly where that turn ran, and the user moves it themselves, because a conversation is not a work product. The gate blocks only entry: a card already in Review is left alone whatever the agent does, and running work lands in In Progress unconditionally. An absent, `null`, or blank agent value keeps the old, ungated move — that is what "today's behavior" meant on hosts predating the field. Switching a session to build mid-chat opens the gate from that turn on.

Done yields to exactly one signal here: a **running or retrying linked session** pulls the card back to In Progress (uniform with the rule above — whatever agent the session runs as), so rework in the same session reopens the card honestly. Every other snapshot keeps Done: a waiting or idle state never rewrote it, so a turn ending after the pull-back re-lands the card in Review with a fresh marker, while a rework that ran and finished entirely while the board was closed simply waits — the user replying in the session restarts the pull-back. A save failure here doesn't retry on every subsequent snapshot (a live session's `onSessions` snapshot fires continuously while it runs): `lastAttemptedStatus` tracks the status this mount last attempted for a task, and only a genuinely different target status is retried, cleared on `Refresh`/reopen.

### The auto-done rule (the board can write Done itself)

One deliberate exception to "you click Done": a Review card that has been visited and whose project carries commit evidence is set to Done by the board itself. Chosen scope (Libio): any task in Review however it landed there; no quiet window (it fires as soon as the session stops); always on, no setting. The pieces:

- **The predicate**, `autoDoneCandidate` in `src/domain/boardView.ts` (pure): status `review`; **visited** — the `needsAttentionSince` marker cleared, *or* the host snapshot reports the session `unread: false` (the chat was opened anywhere — OpenCode sidebar, mobile, another device; this is the out-of-band review signal — `null` on hosts predating the field behaves as before); the session **stopped** — a linked session must be trusted-idle with any outcome but `failed` (unknown state waits: it might be running, and the live sync would yank the card straight back to In Progress), a waiting snapshot never qualifies, and no linked session at all also qualifies; and **commit evidence** in one of two modes:
  - **Project root** (the common case — every session this board starts runs in the project root, `worktree: false`): the task carries `sessionLinkedAt`, the moment its session was linked. Recorded by every flow that writes the link — Start Agent, the rail's chat button (`buildLinkPatch`), explicit linking in the detail dialog, and adoption, which anchors at the session's own `createdAt` so its pre-adoption work still counts. Old records without the field are backfilled with the task's `createdAt` on the board's next load (one silent save per task). Clearing the link (unlink, or its session archived) also clears the anchor — evidence dies with the session.
  - **Worktree** (the original design's path, backward compat only): a worktree directory plus a recorded `sourceBranch`. No current flow ever records the branch, so real tasks never fire this way; the mode stays for any future flow that starts writing it.
- **The evidence**, the host-only service route `GET /commits-ahead` (`src/service/server.ts`, alongside `/branches`) with exactly one mode at a time: `?directory=&base=` runs `git rev-list --count <base>..HEAD`, the project-root mode `?directory=&since=` turns the epoch-milliseconds anchor into git's space-separated ISO date (`2026-11-18 10:00:00 +0000`) and runs `git rev-list --count --since <utc> HEAD`; both then `git rev-parse HEAD`, and answer the same `{ ahead, head }`. Ref and since pattern-checked before git ever sees the composition; `base` and `since` together are a bad request. Any failure is unknown evidence — the rule does not fire, silently. In the project-root mode "commits" means any commit in the project newer than the anchor, in commit-date terms: a concurrent second session committing in the same project counts as this card's evidence too (the user's serial flow makes that rare, and the drag-back guard below bounds the damage); the same window never expires, so a card deliberately unlinked keeps firing only while someone still commits to its project — which is why unlinking retires the anchor.
- **The watcher**, `src/host/autoDoneSync.ts`: fed by `setTasks` and by trusted snapshots (`sessionSync`'s `onLiveChange`), event-driven only, no timers. It picks the evidence mode from the task's own shape (worktree+branch → base mode, else → the anchor and the project's directory from the page's live project list; an unknown project stays quiet), and also carries the **observed-read convergence**: a snapshot with `unread: false` and a stored marker clears that marker and saves (the visit happened, it just did not pass through this board — badges and unseen counts converge on the next load; the rail, display-only, checks `unread` directly in `buildBoardItem`). Commit checks are deduped per task (in-flight set) and spaced by a 60 s retry floor so a host without the local service never hammers it per snapshot. All failure paths are silent — background sync never toasts its plumbing.
- **The write**, `autoDoneMove` in `src/store/taskOps.ts` beside `statusMove`: Done, kept rank, marker cleared, plus the rule's guard — `src/domain/task.ts`'s optional `autoDoneCommit` field records the HEAD hash at fire time in either mode (schema stays v1, the `needsAttentionSince` convention). **Nothing re-fires while HEAD matches the guard**, so dragging the card back out of Done holds until a newer commit actually lands; a new commit in a re-opened card cycles it cleanly (rework → pull-back → Review with a fresh marker → visited → stopped → newer commit differs from the guard → Done again). In the project-root mode the guard is the project's HEAD, so any later commit anywhere in the project re-arms a dragged-back card — same caveat as the evidence window itself.
- **The failure surface, deliberately empty.** The ✓ stays exactly what it was — and is now the only road left for cards the rule can never qualify: no anchor and no worktree, a failed turn, unknown session state. It suggests, `autoDoneSync` acts when the evidence is complete, and both say "Done" in the end.

### The looks-done affordance (the ✓)

OpenChamber's own In-work runtime answers "when does finished work look done?" with a classifier-backed **hint after a measured quiet window — never a write** ("the user closes; this runtime never does"). The board ports the pattern onto signals the guest SDK already receives (`activity`/`outcome`/`updatedAt`; no extension-reachable classifier and no answer text exist in the SDK, so its precision is traded for a two-shot design: Review is an intermediate state and Done stays a click — plus the auto-done rule above, which writes Done when the visit and the commits both say it, and stays silent when they do not). Pure derivation in `src/domain/boardView.ts` (`looksDoneFor`, `looksDoneTooltip`, `nextLooksDoneTickAt`, `LOOKS_DONE_QUIET_MS` = 10 minutes, the number OpenChamber measured for the same hint), rendered by `kanbanView` on the page:

- A linked session `idle` + outcome `completed` while the **stored** status is `review` and the session has been quiet for the window clocked from `needsAttentionSince` (or the session's own `updatedAt` when no marker exists) shows the state: **hint** while the task is unseen — the success-tinted ✓ beside the ⋯ menu, always visible; **quiet** once the task was seen in either sense — the marker cleared here, or the host reporting the chat opened elsewhere (`unread: false`) — the same ✓ muted, revealed on hover/focus like the ⋯ menu (always visible under a finger, which has no hover). Page cards only — the rail carries no looks-done chip: its pill already reads finished, and its always-visible ✓ at the row's edge is the action.
- Any activity change (`running`, waiting, `failed`) voids the state by itself — a new turn re-runs the clock through the same derivation. A task at any status other than stored `review` shows nothing, and `done` of course never does.
- The tooltip names the quiet time ("Looks done · quiet 14m — click to mark Done") while it is still short: the count drops after an hour, both in the label and in the timer that keeps it fresh — `nextLooksDoneTickAt` returns the earliest time-based change (window crossing or next tooltip minute) and the page's `scheduleLooksDoneTick` re-renders on exactly those instants, its only time-driven render. Everything else arrives through snapshots and saves.
- The ✓ click is the user's own Done: it routes through the ⋯ menu's Move-to path (`statusMove` to `done` — kept rank, marker cleared, shared save/rollback). The rail supplies no `onLooksDone`; its Done write is its own always-visible mark-done ✓ (`onMarkDone`).

## Automatic unlinking

A task's links must not outlive what they point at. When a session is deleted, the linked task is deleted automatically. When a session is archived, or a worktree is deleted (all from OpenChamber's sidebar), the corresponding link is cleared from the task automatically — `sessionId` for a session (and with it the auto-done rule's `sessionLinkedAt` anchor, whose evidence window must not outlive the session), `worktree` for a worktree. The task itself is kept for archive/worktree cases, with its title, column, and description untouched; it simply becomes a plain unstarted card again, so **Start Agent** or **Link an existing session** can be used on it fresh. The status is deliberately left alone too — moving or archiving a card's session is not a status change.

Two mechanisms cover it, because a page-type extension only runs while it is the selected view:

- **Live** — `src/host/sessionSync.ts` reports a deleted or archived session on its existing `onSessions` subscription (no extra subscription); `src/host/worktreeSync.ts` does the same for worktrees via one `onWorktrees` subscription per project holding worktree-linked tasks. `src/domain/unlink.ts` (`sessionLinkState`, `worktreeLinkState`) decides: an archived session (`archivedAt`) is archived; an absent one is deleted only when the snapshot finished loading (`state: 'ready'`) and, for the directory the session was last seen in, the per-directory `coverage` finished too. Anything less is `unknown`, and **unknown never deletes** — an incomplete list is not a disappearance, and a false "gone" would lose the task permanently.
- **On every load** — `reconcileLinks` in `src/ui/board.ts` runs at the end of every `reload()`, before the orphan watcher starts: for each project holding linked tasks it fetches the current sessions and worktrees once (`fetchSessions`, which returns both active and full top-level session lists, and `fetchWorktrees`) and deletes tasks or clears links that provably no longer resolve. This is what catches the common case — deleting or archiving in the sidebar while the board is closed, where no live watcher was running. It runs before orphan adoption starts so a session whose stale task is being deleted can never also be re-adopted as a duplicate task.

Unlinking shows a toast naming the task. On a load-time pass it is one summary toast instead of one per task. A save failure falls back to a full reload, which re-loads the still-linked task and lets the next pass retry.

## Auto-adopting a session with no task

A session with no task pointed at it, created at or after a persisted watermark timestamp, becomes a new task automatically — In Progress while running (whatever agent it runs as), Review once the build agent needs attention (question, permission prompt, finished, or failed) — using the same `statusForSession`-derived mapping (`initialStatusForNewSession` in `src/domain/autoTask.ts`), linked to that session, titled from the session's own title (or `"New session in <project>"`/`"New session (<short id>)"` when the host's own id-as-title fallback would otherwise show a raw session id). The build-agent Review gate rides along: a session running as anything else reports nothing while finished or waiting, so it is never adopted for a *finished* conversation — a card appears for it only once a new turn of its own starts running. **Every open surface adopts** — the full-screen page, its expanded-panel twin (the same factory), and, as one implementation, the narrow rail mirror (scoped to its locked project; show-all covers every registered project) — so "the board adopts while it is open" holds whichever board surface that is: the write itself is one, `adoptOrphanSession` in `src/store/adoptOps.ts`.

- `src/store/adoptOps.ts` (`adoptOrphanSession`) is the one adoption write. It reads storage freshly, never the caller's in-memory list, so a session another surface adopted moments ago (or a task linked to it in between) returns `null` before anything is written, and the rank comes from the real end of the real column. After its save it reads once more and converges the race two open surfaces can still lose — both fresh reads passing before either save lands, both saving the same session in the same instant: the record with the smallest task id survives (deterministic for every side — the loser deletes its own record, the winner deletes every rival's, `deleteTask` of an already-deleted key a no-op), every caller hears the survivor, and only the winner announces; the loser's view converges on this surface's own adoption, silently, with no second toast and no ghost card.
- `src/host/orphanSessions.ts` (`watchOrphanSessions`) is a live reporter: one `onSessions` subscription per registered project, reporting every structurally-adoptable session (not a subagent, not archived, not already linked) with a resolvable status, on every snapshot. Sidebar-created sessions are therefore adopted by whichever surface is open, and are also found on the next load of one if they were created while no surface ran.
- `src/store/orphanWatermark.ts` holds the single cutoff: set once, the first time this feature ever runs from any surface, to that moment, and never moved again. Every session's real `createdAt` is compared against it on every load.
- `attemptedSessions` on each surface guards against retrying a failed adoption on every snapshot tick (cleared on `Refresh`/reopen on the page; on the mirror the mount's lifetime is the guard's), and each surface keeps its own exclusions: `dismissedSessions` re-read on every load, plus every linked session id.
- `startingAgents` on each surface temporarily pauses adoption while that surface's own `startSession` request is in flight (Start Agent on the page, the chat button on the rail). The host can publish the new session before that request returns its id; once returned, the id is claimed — before the pause lifts — and the originating task is saved with the link before navigation. A final same-session check removes any duplicate card already linked to that session, and the shared op's post-save convergence now also closes what could once leak through that same-instant window on a watched session.
- Subagents and archived sessions are never adopted. A toast announces each adoption (the winner's, when two surfaces raced).
- **The title promotion closes what adoption's timing opens.** Adoption writes the card the moment a session becomes adoptable, which is usually before OpenCode's title agent has named it from the conversation (the host reports the session's own id as the fallback title until then) — so the card often lands on the `"New session …"` placeholder and nothing ever revisited it: the live map the boards display from did not even carry the session title. Now it does (`SessionLiveState.title`, filled by `src/host/sessionSync.ts`'s `rebuildLive`, updated on every snapshot like the other fields), and the sweep (`src/host/titlePromotion.ts`, one per open surface, fed by `setTasks` and by trusted snapshots through `sessionSync`'s `onLiveChange`, the auto-done rule's channels) offers each linked card still sitting on one of adoption's placeholder texts (`adoptionPlaceholderTitles`, pure, rebuilt exactly) the first real title it sees (`isRealSessionTitle`: trimmed, not the id). The write is one and shared, `promoteSessionTitle` in `src/store/titleOps.ts`: it re-reads storage freshly — a card renamed in the other surface is never clobbered, a card already promoted converges silently (`promoted: false` carries the fresh record) — clamps to the 200-char cap, and saves. Both surfaces promote to the same value, so no tie-break; at most one attempt per session per mount (the same never-forget guard adoption keeps), a `Refresh` resets it, and every failure path is silent. Fill in once: after the first promotion the card is its own name, and later session renames change nothing.

## Start Agent

Shown in the task detail popup at the top of its **OpenCode session** section until a session is linked (after that, Open Chat/Unlink instead, with the chat's own title leading the row and the id in mono under it). Requires a title, description, and project; disabled with an inline reason otherwise, re-evaluated live. It always starts from the project root — the SDK's `false` worktree — so there is nothing to pick: no "Start from" radio, no branch or worktree fields. And it sends nothing: the chat opens with its composer pre-filled from the description (see the steps), and the agent only starts at the user's send.

### The dialog's structure

The popup reads top-down as the task does: head, fields (Title and Project share the first grid row — what names and places the task at a glance; the Description owns the width under it), the task-body actions row directly under those fields (**Delete** left — the kit's destructive red like the board's own danger buttons, its first, arming press filling the button as the selection bar's armed Delete does — **Save changes** right, no divider line, hard against what the buttons write), then a **Status** section carrying only the strip, and finally the **OpenCode session** section (**Start Agent** with its gating hint, or the linked session row; then "Or link an existing session"). The head names the task — the title, kept current while you type, over `Task · <id> · project <name>` in mono — with the agent's live pill beside it when a trusted snapshot covers the linked session, and the **✕** closing at the head's right edge (plain close, no save prompt, the old footer Close's exact semantics). The status strip replaces the old select + "Move to" button pair: one pressed button per status, a press moves immediately through the kept-rank, marker-clearing path (`quickStatus`), and focus stays on the strip after the press so keyboard users can move again. **Unlink** joins **Delete** in needing a second, confirming press. The popup is `aria-modal`: initial focus lands on the dialog itself (no on-screen keyboard on touch), Escape yields first to an open SDK popup or active dictation (the kit's Escape handlers prevent-default before bubbling here), and Tab is trapped inside — SDK popups mount inside the dialog's DOM (`popup.js`'s `openPopup` appends to the trigger's wrap), so the trap's query at press time already includes them. The error banner shows at both ends of the scrollable dialog — Start Agent and the link picker sit in the bottom half, Save in the middle.

Clicking **Start Agent**:
1. Passes the title, description, and project currently shown in the dialog, including edits not yet saved with **Save changes**. The current values are also saved to the task as part of the session-link update.
2. The session title uses the task title. If the title is still the default `"New task"`, `sessionTitleForTask` uses the first line of the description instead. This avoids giving a new session the generic task placeholder as its name.
3. Calls `host.startSession` with `worktree: false` (the root), **no `text`**, and `navigation: 'preserve'`. Adoption is paused during that request because the host can publish the new session before the request returns its id.
4. When a session id returns, it is claimed in `attemptedSessions`, and the existing task is saved with that id, the latest title and description, the project, In Progress status, its worktree (`resolveTaskWorktree` — a root start reports only what the host echoes back), and the auto-done rule's anchor (`sessionLinkedAt`, the save's own moment). The save retries three times with backoff (`saveTaskRetrying`). A same-session check removes an already-created duplicate task if one exists.
5. Clears the saved open-task preference and waits for that storage write to finish before calling `host.openSession(result.sessionId)`. The dialog therefore does not reopen when the user returns to the board. An `openSession` failure toasts, the dialog still closes, and the flow stops — the chat exists, is linked, and opens from its card.
6. Populates the prompt through `fillComposerAfterOpen` (`src/host/promptFill.ts`): the description (`chatPromptForTask` — the title when the description is empty) with `send` omitted, replace-composed onto the now-current session's composer. Nothing is sent; the agent only starts at the user's send. The first write goes out in the same task `openSession` resolved in — before the dialog closes — and a settled second write repeats it once the host's switch commit has flushed, because a fill issued immediately can silently lose the switch race ("The composer fill has no per-session targeting" under the SDK limitations; same as the rail's own chat action). A fill that is provably gone toasts quietly; the text stays safe on the task.
7. On failure (`sessionId: null`), surfaces the host's own failure reason and keeps the worktree's directory in the message rather than deleting anything.

## The local service (git branches + voice dictation)

Declared via `contributes.service` with `permissions.exec: ["git"]` — the only way to list a repository's real branches, since the SDK itself has no API for this (confirmed by enumerating every `HostClient` method). The same process also answers the dictation routes; it runs no new external programs for that (sherpa-onnx is loaded in-process). Since the detail dialog's Start Agent was simplified to a root-only start, the board no longer calls the branch route (no base-branch dropdown to fill) — the route and its exec permission remain declared from the older dialog, nothing in the UI exercises them.

- `src/service/main.ts` is a thin bootstrap (env, git implementation, real recognizer); `src/service/server.ts` builds the HTTP surface: bearer auth, `GET /health`, `GET /branches`, `GET /commits-ahead` (the auto-done rule's commit check, in both its base and since modes), and the `/transcribe*` routes. Built to `service/main.js` (Node/ESM target, not the browser build) — the host spawns it and proxies to it on `127.0.0.1`; every request is bearer-authenticated by the host itself, and the panel never sees the token or dials the port directly.
- The branch route runs **exactly one command**: `git -C <directory> for-each-ref --sort=-committerdate --count=200 --format=%(refname) refs/heads refs/remotes` — read-only, most-recently-active branches first, capped at 200, for a project directory the panel already knows about (`path.isAbsolute` checked).
- `src/host/branchService.ts` (`fetchServiceBranches`) is best-effort: not approved, not running, a bad answer, or any other error all become `null`, never an exception the UI has to handle, because the worktree-derived fallback was a complete, working option on its own. Unused by the UI today; kept only with the still-declared route and permission.

## The agent channel (agents read the board, queue tasks and notes)

An OpenCode session in one of the board's projects can talk to the board through the extension's own local service. The design's one non-negotiable: **the board page is the only writer of task records** — the service has no `host.storage` access (nothing in the SDK grants it), and the page is often closed. So every agent write is *queued*, never applied, and the channel is a two-way sync with the page:

```
agent --HTTP(loopback, agent token)--> service --journal--> [board page loads] --> host.storage
   ^                                      ^
   |                mirror.json <--PUT-- board page (debounced after every write)
   read GET /agent/tasks
```

Pure wire model in `src/domain/agentChannel.ts`; the service side stores it in `src/service/agentStore.ts` and serves it in `src/service/agentRoutes.ts`; the board's best-effort client is `src/host/agentChannel.ts`.

### Two tokens, one surface

`server.ts` now authenticates two bearer tokens on the same loopback listener:

| Token | Held by | Reaches |
|---|---|---|
| `OPENCHAMBER_SERVICE_TOKEN` (host's) | the host proxy only | everything, as before — `/branches`, `/transcribe*`, **and** the channel's sync routes |
| the channel's agent token | whatever the user's own processes can read | `GET /agent/tasks`, `POST /agent/tasks`, `POST /agent/tasks/:id/note` — nothing else |

The agent token is minted once per install (32 random bytes, `agent-token` in the service data dir, mode 0600) and advertised in `agent.json` (`{ v, port, token, pid }`, mode 0600, temp-file + rename on every spawn, **removed on SIGTERM/SIGINT** so a clean stop never advertises a dead port; a crash leaves a stale port that answers only `ECONNREFUSED`). The trust line is stated plainly in the README: any process running as the user can read the token, which is exactly the trust every agent session already has on this machine — the SDK's own "least exposure, not a sandbox" stance applied to a local file.

The scope split lives in the route handler, not in the server: an agent token on `/agent/pending`, `/agent/pending/ack`, or `/agent/mirror` answers 403, and on the historical routes (`/branches`, `/commits-ahead`, `/transcribe*`) the whole subtree answers 403 — the agent token must never reach git or dictation. The sync routes accept the host token only; **an agent can neither read the journal nor acknowledge it**, so it can never erase what the board has not yet applied.

### The mirror (reads)

The board pushes a mirror document — tasks as `AgentTaskView`s plus the project list (`id`, `name`, `directory`) — debounced 500 ms after every `setTasks`, skipped while the live project list is empty (a map-less mirror is worth less than none; the next change, load, or event re-tries), and best-effort throughout: `serviceRequest` failures are silent, because the service may be unapproved, paused, or mid-restart (it now runs with `keepRunning: true`, so it holds while OpenChamber runs).

`buildMirrorDoc` is where the 64 000-character `serviceRequest` body cap meets a real board: it cuts in measured, declarative steps — full descriptions; descriptions clamped at 1500; at 400; descriptions empty; tasks capped to the 60 most-recently-updated with notes dropped — each step applied cumulatively, tasks ordered oldest-first so the over-cap truncation drops the *oldest* rows, newest work always represented. A mirror smaller than the truth is honest about exactly that (the skill says descriptions in listings are summaries); it never lies about existence or status.

The route `GET /agent/tasks` serves the pushed document as it parses; no per-task route exists (the mirror is the summary by design).

### The journal (writes)

`POST /agent/tasks` and `POST /agent/tasks/:id/note` validate the request the `parseTask` way (throw with a human reason, so the agent's tool result says what to fix — a description is refused, not silently clamped), map `directory` → `projectId` against the mirror via `resolveDirectoryToProject` (exact match, else the longest registered directory that prefixes it on a path boundary — `/record` never matches `/repo`), and append a journal entry (`journal.jsonl`, entry ids `a_<16 hex>` so corrupt lines are skippable individually and acks are id-precise). The answer is a receipt — **queued, not created** — with the resolved project named and, when a directory matched nothing, a `warning` that says the task will land unplaced. A journal at `AGENT_JOURNAL_MAX` (200) answers **429** naming the catch-up step instead of losing the write. Every accepted append fires `emit('kanban-agent-change', { pendingCount })` through `createServiceHost` — open board frames re-pull live; frames that are closed hear nothing replayed, which is why the journal is on disk, not in memory.

### The board applies

`reload()` runs `applyAgentPending()` after link reconciliation and before the orphan watcher (the same ordering discipline: what lands here saves through the same task records the adoption reader walks, and pending creates are never orphans). The pull → `planPendingApply` (pure) → per-entry independent saves → ack only what landed:

- **Creates** become real tasks through `createTask` with `rankAtEnd(tasks, status)` — the same end-of-column landing a quick-created task gets; status limited to `backlog`/`todo` at the wire. The entry's service-time `projectId` is used only when that project still exists; otherwise the *board's* live project list re-resolves the directory (fresher than the mirror), else `null` — unplaced, never misplaced. Ids are board-minted (`newTaskId`), plan-time; a note arriving for a task is folded by task so five notes in one journal are one save.
- **Notes** land on `task.agentNotes` (cap: `AGENT_NOTES_MAX` = 20 per task, oldest give way; `AGENT_NOTE_MAX` = 2000 chars each, `appendAgentNote` clamps the way dictation does). The detail dialog renders them newest-first under "Agent notes".
- **Acks** remove only the applied/dropped ids from the file; a save failure leaves its entry pending and the next pull (next load, next event, next Refresh — the banner says so) retries it. A replayed create would be a duplicate card, so a *failed ack* is treated as a failed apply: the board reloads from storage rather than guessing which ids stuck.

Toasts follow the board's voice (`From an agent: added "…" (Backlog), an agent left a note on "…".`), and applying is guarded by one in-flight flag — the event-driven pull and the load-driven one never interleave.

### What the channel cannot do

By design, and enforced in three places (route surface, wire validation, board apply):

- No deletes. No status moves. No Done. Statuses belong to the linked session's own activity (`statusForSession`), and Done is the page's alone — your clicks and the page's own auto-done rule (`autoDoneSync`), never the agent channel, never the rail. The mirror has no write path for any of it.
- Notes are additive and capped; the agent token cannot read or ack the journal; the mirror accepts only the board's push.
- No session correlation arrives with an agent's HTTP call (routes are curl-level), so notes are not attributed to a session — an MCP wrapper (`ai.opencode/sessionID` arrives in tool-call metadata for free) is the natural later addition, which is why the routes were kept plain.

## Voice dictation (description field)

A **🎙 Dictate** button sits under the description textarea in the task detail dialog. It is rendered only when the host offers the microphone (`ready.features.microphone` from the `microphone` grant); everywhere else it does not exist, and the documented fallback — particularly in the native mobile app — is the operating system keyboard's own dictation.

### Flow, tap by tap

1. **First tap** — `host.openMicrophone()` runs inside the click (the frame's audio graph needs the user's gesture; the SDK creates its `AudioContext` before its first await). The guest attaches a `ScriptProcessor` graph fed by the returned `MediaStream` into a *silent* `MediaStreamDestination` (never the speakers) and starts pushing one `Float32Array` copy per callback. The button flips to **⏹ Stop and insert**, a status line shows the elapsed time, and a **Discard** button appears.
2. **Second tap** — stops the capture immediately (`mic.close()`, so the host's red "using your microphone" indicator goes away), concatenates the chunks clamped to `MAX_CLIP_SECONDS` (120 s), and transcribes.
3. **Transcription** — `src/ui/speech.ts` resamples to 16 kHz (box-average when the device rate divides evenly, linear interpolation otherwise), encodes Int16 PCM, base64-chunks, and streams via `serviceRequest`: `POST /transcribe/begin` → one `POST /transcribe/append` per chunk → `POST /transcribe/finish`, all carrying one clip id. The returned text is appended to the *existing description* with a single space (clamped to `DESCRIPTION_MAX` if it would overflow; the title is never touched), the field is focused, and unsaved-state marking stays consistent.
4. **Discard / cancel / teardown** — the discard button, closing the dialog, Escape, overlay click, or the board being disposed all route to the same cancel path: the microphone is closed right away, partial audio is dropped, an in-flight upload is abandoned (a generation counter makes late completions inert) plus a best-effort `POST /transcribe/cancel` so the service frees the clip. A host-side stop (`revoked`, `device-lost`) triggers the same reset with a toast.
5. **Errors** — denied/unsupported microphone and service failures surface as `host.toast` messages with human wording.

### Service transcription routes

Audio sent as base64 Int16 PCM at 16 kHz. A single request body on the wire carries at most `GUEST_REQUEST_BODY_MAX` (64 000) characters — roughly 5.7 000 base64 bytes of PCM ≈ 1.35 s of audio per chunk (`PCM_CHUNK_BYTES` = 43 200 bytes) — hence the chunked flow. The clip store accepts at most 4 concurrent clips, 120 s of audio each (the same cap the guest enforces), and expires idle clips after 5 minutes. The one-shot `POST /transcribe` remains for callers that already hold a whole short clip.

| Route | Body | Answer / errors |
|---|---|---|
| `POST /transcribe` | `{ pcm16, sampleRate }` | `{ text }`, or 400/413/503 |
| `POST /transcribe/begin` | `{ sampleRate }` | `{ id }`, or 400/429 |
| `POST /transcribe/append` | `{ id, pcm16 }` | `{ samples }`, or 400/404/413 |
| `POST /transcribe/finish` | `{ id }` | `{ text }`, or 404/503 |
| `POST /transcribe/cancel` | `{ id }` | `{ cancelled }`, idempotent |

Non-2xx answers carry `{ error: "<human-readable reason>" }`, which the dialog turns into a toast.

### The recognizer

- Package: `sherpa-onnx-node` 2.0.1 (with the `sherpa-onnx-linux-x64` 2.0.1 platform package carrying the native binding). Loaded **lazily on the first transcription**, never at service spawn, so `/health` stays instant and a never-used mic costs nothing. The binding stays outside the esbuild bundle (`external: ['sherpa-onnx-node']`) because it loads its own `.node` file and shared libraries at runtime.
- Model: `~/.config/openchamber/speech-models/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8/` (NVIDIA Parakeet TDT 0.6B v2, int8, offline NeMo transducer), **read-only** — the service never writes to it and never downloads anything. Recognizer config matches sherpa-onnx's own Parakeet example: `featConfig {sampleRate: 16000, featureDim: 80}`, `modelConfig {transducer: {encoder, decoder, joiner}, tokens, numThreads: 2, provider: 'cpu', modelType: 'nemo_transducer'}`.
- First-use latency pays that load (~1.5 s measured on this machine); a 7 s clip decodes in ~0.5 s afterwards (RTF ≈ 0.06, two threads). A clip of the 120 s cap still finishes well inside the host's 20 s `serviceRequest` timeout once loaded.
- If the model directory or its four files are missing, the service stays healthy and every transcribe route answers a clear 503 (`Speech model not found: …`) instead of crashing; clips of genuine silence never touch the model at all.

No audio, text, or transcript ever leaves the machine: capture is the host's own microphone, upload is over the service loopback, and decoding is local ONNX.

## Known SDK limitations

- **No API to list a repository's full branch set**, only `GuestWorktree.branch` per existing worktree, or the local service above.
- **Capability approval is all-or-nothing** across the whole manifest (see above) — there's also no cross-extension service API, so a capability can't be split into its own, separately-optional package either.
- **The microphone cannot be opened at a chosen rate.** `host.openMicrophone()` takes no arguments — the SDK builds the frame's `AudioContext` at the device's default rate (typically 48 kHz) and the host captures at that rate, so the guest downsamples to 16 kHz itself (see `src/ui/speech.ts`). The capture also reaches the guest only as a `MediaStream`, requiring the SDK's own `ScriptProcessor`-into-silent-destination pattern to pull samples.
- **The composer fill has no per-session targeting.** `host.prompt` with `send` omitted (and `host.compose`) writes the host's single pending composer slot (`setPendingInputText`, verified against the installed host's own guest bridge); only the editor showing the *current session* at consume time picks it up, and there is no API to target another session — the host's own new-session draft rides that same slot with its `initialPrompt`. The store also refuses the write while the guest frame has no switched session context (`NO_SESSION`). `openSession` resolves before the host's switch commit lands, so a fill issued right after it races that commit: an editor still showing the old session, or the switch's cleanup writers, can consume or clear the slot first, and the host answers `{ sent: 'skipped' }` for the write either way — a lost fill is silent. Which surface wins depends on layout: the rail's single always-mounted chat editor consumed the immediate write every time (so rail quick-opens always filled), while the expanded panel's reflow, and a page whose chat area mounts only after the switch, could not. `src/host/promptFill.ts` (`fillComposerAfterOpen`) is the answer: write immediately, then write the same text once more once the commit has settled — the settled write meets the new chat's mounted editor; a landed first write makes it a re-set of that text (and re-focuses the composer, suiting the review-or-edit-then-send flow), and a text typed inside the settle window (~0.7 s) would be replaced by it. The guest bridge additionally refuses compose while the frame's session context is not yet switched (`NO_SESSION`), which the settled write also rides past.
- **A `serviceRequest` body is capped at 64 000 characters** (`GUEST_REQUEST_BODY_MAX`) — roughly a second of 16 kHz Int16 audio per request — so longer recordings are streamed as ordered chunks through `/transcribe/begin|append|finish`. Responses may be up to 8 MB, so `{ text }` is never a problem.
- **Chats are invisible.** A chat (a session with no project) is explicitly documented as outside any project; the `sessions` capability's methods are all scoped to registered projects. There is no SDK method to list or watch chats at all.
- **Session auto-adoption runs only while the Kanban page is active**, plus the next time it opens. A session started from the sidebar while the board is active is adopted live; one started while the board is closed is found when the board opens again, if it meets the watermark and activity rules. A session started from a task is linked directly to its existing task instead of being adopted as another task.
- **No way to set a worktree's folder name independently of its branch name** — `startSession`'s `{ kind: 'new', name }` sets both together.
- **OpenChamber's own worktree-creation can fail with "Remote branch not found" for a branch confirmed to exist on the remote and already fetched locally.** When `host.startSession` rejects for a new-branch request, the real reason doesn't survive the trip back to the extension — only a generic failure does — so the error shown names the base branch involved and suggests this is a known possibility, not a claim that the branch name is wrong.

## Install and verify

```bash
git clone <this repository>
cd openchamber-kanban
npm install
npm run check   # typecheck + unit tests + build panel/main.js, panel/page.js, service/main.js
```

In OpenChamber: **Settings → Extensions → Add** → paste this folder's absolute path → approve `sessions`, `prompt`, `microphone`, and the local service → open **Kanban** either beside a chat (the rail icon: the quick-actions mirror at rail width, the interactive board once the panel is expanded — desktop) or as the full-screen page from the Extension pages menu above the session list. The mic button appears in a task's detail dialog only where the host actually offers the microphone (desktop/web with SDK 2.7.x); on mobile the fallback is the OS keyboard's dictation. Updating from an older version asks to re-approve once — the service now announces it **keeps running** (that is what makes the agent channel reachable whenever an agent runs), and OpenChamber re-asks whenever a package asks for more than before.

Acceptance scenarios:

1. Create three tasks, reload OpenChamber → all three persist.
2. Drag a task between columns, reload → the new status persists.
3. Link an existing session to a task → **Open Chat** → the real session opens via `host.openSession`.
4. Edit a task title and description without clicking **Save changes**, then start an agent → the current values are saved, the chat opens with the description pre-filled in its composer and nothing sent until you press send, the same task links to the session, and the task moves to In Progress.
5. Run two tasks concurrently → they never share a session id.
6. A build agent finishes a turn → the task moves to Review, never to Done (Done comes from your click, or from the auto-done rule below). A session running as any other agent never moves its task to Review.
7. Start a session from the OpenChamber sidebar → one new task appears for it, in the column its activity implies.
8. Start an agent from a task → only the originating task is linked to that session; no second task is adopted for the same session.
9. Open a task's detail dialog on desktop → 🎙 Dictate → speak a sentence → Stop and insert → the sentence appears at the end of the description (title untouched), the red microphone indicator disappears the moment you stop, and a second dialog with the mic button already off starts no capture.
10. A build agent finishes a turn → the task lands in Review; after ~10 minutes of the session staying idle and `completed` with no new turn, the Review card shows the success-tinted ✓ with a tooltip naming the quiet time; opening the card turns the ✓ muted (hover to see it); clicking it marks the task Done — your click, always. If the task's worktree instead carries commits ahead of its source branch, the auto-done rule beats you to the click: once you have visited the card (here or anywhere its chat opens) and the session is quiet, the board writes Done itself, silently.
11. Check two cards (or Ctrl/⌘-click them) → the selection bar shows "2 selected"; Move to a column keeps their relative order at the target's end, Mark Done sends both to Done, and Delete — after a second, confirming press — removes both and dismisses their linked sessions from adoption. Escape clears the selection; the rail panel shows no checkbox, bar, or trash anywhere.
12. Open the board once (the mirror is pushed), then from a terminal read the agent token in the service data dir, `GET /agent/tasks` (tasks listed), `POST /agent/tasks` with the repo's directory (receipt says `queued`, project named), close the board, reopen → the card lands at the end of Backlog with a "From an agent …" toast; `POST /agent/tasks/:id/note` on its id, reopen → "Agent notes" in the detail dialog shows it, newest first.
13. With the agent token: `/branches`, `/commits-ahead`, and `/transcribe/cancel` answer 403; `/agent/pending`, `/agent/pending/ack`, and `/agent/mirror` answer 403. With no or a wrong token: 401 everywhere but `/health`. After `SIGTERM`, the data dir's `agent.json` is gone.
12. First press of a column's head trash arms it ("Click again to empty"); the second deletes exactly that column's visible tasks and toasts the count. Left alone, the armed state resets itself after a few seconds; the trash on an empty column never arms.
13. In the rail, click a linked card's chat bubble → the chat opens, and an orange border on the row clears with it (the marker was the review flag).
14. In the rail, click the plus-cut chat glyph on an unlinked card → a chat is created attached to the card, opened, and its composer is pre-filled with the card's description — nothing is sent until you press send, and the card does not change columns.
15. On a desktop, click the Kanban rail icon beside a chat → the quick-actions mirror opens as always. Expand the panel (or drag it wider than ~768 px) → the interactive board mounts in the same frame without a reload — drag cards, open the detail dialog, quick-add; the filter is the one the full-screen page saved. Collapse it below ~512 px → the mirror returns (the board's transient selection resets, tasks untouched). On a phone or tablet the panel shows the quick actions at any width, and the full-screen page still opens from the Extension pages menu on every host.
16. Auto-done end to end: connect a task to a session in a project worktree, let the agent commit twice, wait for the turn to finish (card lands in Review with its unseen flag), then open the card and close it → the marker clears; on the next quiet snapshot the board itself moves the card to Done (no toast, no ✓ needed). Drag the card back to Review without new commits → nothing re-fires, the guard holds. Reply in the session so it runs → the card drops back to In Progress, then finishes into Review again, and with a new commit the rule may fire once more.
